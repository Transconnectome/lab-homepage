# Connectome Lab 홈페이지 — 연구 소개 심화·검증·구현 프롬프트

현재 작업 중인 서울대학교 Connectome Lab 홈페이지의 연구 소개를 평가하고, 부족한 내용을 조사·재구성하여 실제 페이지에 반영하라.

이번 작업의 최우선 목표는 디자인 변경이나 글자 수 증가가 아니다. 방문자가 연구실의 중요한 질문, 접근의 이유, 실제 기여, 남아 있는 문제를 이해하게 만드는 것이다. 기존 홈페이지 작업 지침의 기술·접근성·보안·배포 원칙은 유지하되, 연구 콘텐츠의 근거와 논리가 준비된 뒤 화면 구현을 진행하라.

## 1. 역할과 작업 순서

메인 역할은 ‘과학 편집 책임자이자 구현 책임자’다.

서브에이전트를 실제로 사용할 수 있다면 최대 두 명에게 다음 작업을 명시적으로 위임하라.
- 근거 조사자: 허용된 자료에서 연구별 주장과 출처를 수집한다.
- 비판적 검토자: 초안을 원자료와 대조해 피상성, 과장, 누락, 논리적 비약을 지적한다.

두 역할은 사이트 파일을 직접 수정하지 않고, 근거를 포함한 보고서를 반환한다. 메인 에이전트만 콘텐츠와 코드를 통합한다. 서브에이전트를 사용할 수 없다면 같은 절차를 순차 수행하고, 독립 검토를 받았다고 표현하지 말라.

작업 순서는 ‘현황 진단 → 근거 조사 → 연구 구조 설계 → 본문 작성 → 과학적 검토 → 화면 구현 → 최종 검증’이다. 근거가 부족한 내용을 먼저 그럴듯하게 작성하고 나중에 출처를 붙이지 말라.

## 2. 현황 진단: 무엇이 부족한지 구분하라

README, AGENTS.md, 연구 페이지, 관련 콘텐츠 데이터, 논문·프로젝트 목록, 언어 구성, 자동 업데이트 방식을 읽어라. 관련 없는 비공개 자료나 계정까지 탐색 범위를 넓히지 말라.

연구 주제별로 아래를 표로 정리하라.
‘현재 설명 / 실제 근거가 있는 연구 / 누락된 내용 / 문제 유형 / 수정 우선순위’

문제 유형은 구분하라.
- 자료 부족: 설명에 필요한 근거를 아직 확보하지 못했다.
- 설명 부족: 근거는 있지만 왜 중요한지와 무엇을 밝혔는지가 전달되지 않는다.
- 구조 문제: 좋은 설명이 흩어져 있거나 방문자가 찾기 어렵다.

현재 홈페이지가 연구실의 전체 연구를 충분히 대표한다고 가정하지 말라. 반대로 페이지가 짧다는 이유만으로 부실하다고 판단하지 말라. 진단에는 실제 문장이나 파일 위치를 제시하라.

## 3. 근거 조사: 논문 목록이 아닌 연구별 근거 기록을 만들어라

자료는 현재 프로젝트, 공개 논문·프리프린트·공식 프로젝트 페이지·공개 코드, 사용자가 이번 작업에 제공하거나 사용을 허용한 자료로 제한한다. 영어 원문을 중심으로 조사하고, 작업 보고는 한국어로 한다. 공개 페이지의 기존 언어 구성은 유지한다.

각 연구 분야의 대표 논문과 프로젝트를 선정하고 선정 이유를 설명하라. 최신 자료만 보지 말고, 연구 방향을 형성한 핵심 연구와 현재의 확장을 함께 검토하라. 공개 논문이 적은 분야에 개수를 맞추려고 다른 연구를 끼워 넣지 말라.

제목·검색 요약·서지정보만으로 연구 기여를 작성하지 말라. 핵심 주장에 필요한 서론, 방법, 결과, 한계와 관련 그림 설명을 읽어라. 원문 접근이 제한되면 확인한 범위를 기록하고, 그 범위를 넘는 세부 주장을 쓰지 말라. 원문을 읽었다는 사실 자체를 논문의 결론이 검증되었다는 뜻으로 취급하지 말라.

핵심 주장마다 다음을 기록하라.
‘주장 / 출처·버전·확인일 / 해당 절·그림·표 / 대상·데이터·연구설계 / 실제 결과 / 해석 가능한 범위 / 한계 / 공개 가능 여부’

연구실과 해당 논문의 관계도 확인하라. 공동저자 참여만으로 연구실이 연구 전체를 주도했다고 쓰지 말라. 같은 연구의 프리프린트와 출판본은 별도 성과로 중복 집계하지 말라.

출판·프리프린트 여부와 현재 진행 상태는 별도 항목으로 관리하라. 연구 중, 계획, 편집자가 제안한 미래 아이디어를 이미 입증된 성과와 섞지 말라. 접근 가능한 내부 자료라도 공개 승인이 없으면 홈페이지나 공개 저장소 문서에 옮기지 말라. 출처가 상충하면 충돌을 기록하고 단정하지 말라.

## 4. 연구실의 지적 구조를 재구성하라

분야를 모델 이름, 데이터 종류, 기술 키워드만으로 분류하지 말라. 상위 연구 질문을 중심으로 실제 연구를 연결하라.

각 분야는 다음을 설명해야 한다.
- 어떤 현상이나 문제를 이해하려는가?
- 현재 지식의 어떤 빈틈을 다루는가?
- 이 연구실의 접근과 축적된 연구가 그 문제에 어떻게 기여하는가?

AI·방법론 연구만 부각되어 인지·정서·발달·정신건강·유전·환경 관련 연구가 누락되는지 점검하라. 다만 실제 자료에서 확인되지 않는 분야를 새로 만들어 넣지 말라. 분야별 분량을 억지로 동일하게 맞추지 말라.

연구 방향 간 연결은 구체적으로 설명하라. 예를 들어 한 분야의 결과가 다른 분야에 어떤 가설, 데이터, 표현, 검증 과제를 제공하는지 밝혀라. 모든 분야를 억지로 연결하거나, 근거 없이 위계·성숙도 단계·일방향 발전 과정으로 그리지 말라. 확인된 연결과 향후 연결 가능성을 구분하라.

## 5. 분야별 상세 설명의 필수 내용

각 분야의 본문을 읽으면 다음 질문에 답할 수 있어야 한다. 아래 항목은 편집 기준이며, 모든 페이지를 똑같은 소제목이나 카드로 만들라는 뜻은 아니다.

A. 핵심 질문: 정확히 무엇을 알고 싶은가? 가능하면 대상·조건·비교가 드러나게 써라.
B. 중요성과 지식의 빈틈: 이 질문이 왜 중요한가? 기존 연구가 무엇을 설명하고 무엇을 아직 설명하지 못하는가?
C. 접근의 이유: 왜 이 데이터, 연구설계, 분석·모델링 방법이 필요한가? 기술 이름 대신 질문과 방법의 논리적 연결을 설명하라.
D. 실제 기여: 무엇을 관찰·검증·개발했는가? 선행 접근과 비교해 어떤 지식이나 역량을 추가했는가? 차별성의 범위를 과장하지 말라.
E. 구체적인 연구 사례: 대표 연구를 ‘질문 → 설계 → 결과 → 의미’로 설명하라. 논문 제목과 링크만 나열하지 말라.
F. 해석의 범위와 한계: 무엇은 말할 수 있지만 무엇까지는 말할 수 없는가? 주요 대안 설명이나 일반화의 제한을 설명하라.
G. 다음 질문: 결과에서 어떤 후속 질문이 나오는가? 적절한 경우 어떤 비교·실험이 설명을 구별할 수 있는지 제시하라. 공식 연구 계획이 아니라 새 제안이면 검토용으로만 남겨라.
H. 연구실 전체와의 연결: 이 분야가 다른 분야에 무엇을 제공하거나 어떤 검증을 요청하는가?

‘AI로 뇌를 이해한다’, ‘혁신적인 멀티모달 연구’, ‘정신건강에 기여한다’ 같은 문장만으로 항목을 충족했다고 판단하지 말라. 추상적인 문장에는 구체적 질문, 사례 또는 근거를 연결하라. 배경 교과서 설명을 늘려 연구실의 기여가 있는 것처럼 보이게 하지 말라.

상관·예측·디코딩·생성·기제 설명·인과 검증·임상 유용성을 구분하라. 예측 성능을 곧바로 인과적 이해로, 시각적으로 그럴듯한 생성 결과를 과학적 타당성으로 표현하지 말라. 수치는 비교 대상, 평가 조건, 지표와 적용 범위를 함께 확인하라. 미래의 포부를 현재의 능력처럼 서술하지 말라.

## 6. 깊이와 가독성을 함께 설계하라

콘텐츠는 다음 세 층으로 구성하라.
- 한눈에 보는 소개: 분야의 핵심 질문과 중요성을 1~2문장으로 전달한다.
- 이해를 돕는 개요: 문제, 접근, 대표 기여를 짧은 여러 문단으로 설명한다.
- 상세 페이지: 연구 사례, 근거, 한계, 열린 질문, 관련 논문·코드로 이어진다.

분량을 채우는 대신 각 층이 서로 다른 독자의 질문에 답하게 하라. 기존 언어별 페이지의 과학적 의미와 불확실성 수준을 일치시켜라.

글을 줄여 카드 안에 억지로 맞추기보다, 개요와 상세 페이지를 연결하라. 중요한 연구 설명을 논문 링크 뒤에만 숨기지 말라. 전문용어는 필요할 때 쓰되 처음 등장할 때 뜻이나 역할을 설명하라. 모델 약어를 지워도 연구 질문이 이해되어야 한다.

개념도나 실제 연구 그림이 설명에 도움이 되는 경우에만 제안하라. 장식용 뇌 이미지로 내용을 대체하지 말라. 그림은 출처·사용 권한을 확인하고, 개념도와 실제 데이터를 명확히 구분하라.

## 7. 과학적 품질 검토: 화면 구현 전에 통과해야 한다

각 분야를 다음 기준으로 ‘충족 / 수정 필요 / 확인 불가’로 평가하라.
1. 질문이 특정되어 있다.
2. 중요성과 기존 지식의 빈틈이 설명된다.
3. 질문과 방법 선택이 논리적으로 연결된다.
4. 연구실의 실제 기여가 구체적 사례와 출처로 드러난다.
5. 결과, 해석, 한계, 포부가 구분된다.
6. 연구실 이름을 다른 이름으로 바꾸면 그대로 통용되는 일반론에 머물지 않는다.
7. 비전공자는 핵심을 이해하고, 전문가는 근거를 추적할 수 있다.
8. 주요 연구의 누락·중복·부당한 편중이 점검되었다.

평가마다 해당 문장과 출처 또는 필요한 수정사항을 제시하라. 높은 자기평가 점수나 출처 개수만으로 통과시키지 말라. 참고문헌이 존재하는지뿐 아니라 그 문헌이 해당 주장을 실제로 뒷받침하는지 검토하라.

비판적 검토자는 추가로 아래를 확인하라.
‘독자가 이 연구가 하지 않은 일까지 했다고 오해할 문장은 무엇인가?’
‘중요한 결론을 받아들이지 않을 대안 설명은 무엇이며, 이를 숨기고 있지 않은가?’
‘실제 연구의 지적 기여 대신 모델 크기·저널 이름·성과 수치만 강조하고 있지 않은가?’

검토와 수정을 최대 두 차례 수행하라. 근거를 확보하지 못한 주장은 삭제하거나 범위를 좁히고, 해결되지 않은 항목은 기록하라. 해당 주장을 통과시키려고 근거를 만들어 내지 말라. 문제가 해결된 분야는 진행하고, 미해결 분야 때문에 전체 작업을 무한 반복하지 말라.

## 8. 구현·최종 산출물

검토가 끝난 콘텐츠부터 기존 기술 스택과 디자인 원칙에 맞춰 반영하라. 관련 없는 코드, 사용자 변경사항, URL, 기존 언어 구성을 보존하라. 과학적 검토는 UI 검증을, 빌드 성공은 과학적 검토를 대신하지 않는다.

가능하면 현재 설치된 프런트엔드·브라우저 검증 스킬을 사용하되, 실제 사용 가능 여부를 먼저 확인하라. 스킬이나 도구를 사용하지 않았는데 사용했다고 보고하지 말라.

모바일·데스크톱에서 읽기 흐름, 본문 폭, 제목 구조, 상세 페이지 이동, 논문 링크, 키보드 접근성을 검증하고, 프로젝트에서 제공하는 빌드·테스트를 실행하라. 자동 콘텐츠 동기화가 있다면 검수한 설명을 덮어쓰지 않도록 기존 구조에 맞춰 보호하라.

최종 산출물은 다음과 같다.
- 연구별 개편 전후 진단과 핵심 변경 이유
- 실제 반영한 개요·상세 페이지 또는 구현이 불가능한 경우 즉시 사용할 수 있는 원고
- 공개 가능한 자료만 포함한 주장–출처 대응 기록
- 읽은 자료, 접근하지 못한 자료, 남은 검증 사항
- 변경 파일, 실제 실행한 검증과 결과, 향후 업데이트 방법

대표적인 얕은 설명 2~3개를 골라 수정 전후를 보여주고, 문장 길이가 아니라 무엇이 더 구체적이고 검증 가능해졌는지 설명하라.

공개 전 PI가 확인할 항목은 최소한의 구체적인 결정 사항으로 제시하라. 논문으로 해결할 수 있는 사실 확인을 사용자에게 떠넘기지 말라. 비공개 자료의 공개 여부나 연구실의 공식 입장처럼 사용자 판단이 필요한 사항은 임의로 결정하지 말라.

승인 없이 배포, 원격 push, 도메인 변경, 유료 서비스 가입을 하지 말라. 현재 권한으로 가능한 조사·편집·구현·검증을 수행하고, 계획만 제시한 채 완료라고 말하지 말라.
